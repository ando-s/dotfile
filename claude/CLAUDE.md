# Personal Preferences

s-ando が全プロジェクトで Claude Code に守ってほしい個人的な好み。
プロジェクト固有のルールは各プロジェクトの `CLAUDE.md` を参照。

## コミュニケーション

### 曖昧な抽象ラベルを使わない
- 「ブロッカー」「複雑」「リスクがある」等の抽象ラベルではなく、**具体的に何がどう問題か** を書く
- 例: ❌「複雑なクエリ」 → ✅「3テーブル JOIN + 集計関数の組み合わせで実行計画が読みづらい」

### 英語の専門用語は日本語訳を併記する
- DDD パターン名・アーキテクチャ用語など初出時は「英語（日本語訳）」形式
- 例: 「Bounded Context（境界づけられたコンテキスト）」「Repository（リポジトリ）」

### やり取りの文脈をドキュメントに持ち込まない
- 「○○さんが言った」「以前この方針だった」等の会話文脈はドキュメントに書かない
- ドキュメントは現時点の事実・決定だけを記述する

## 議論・回答

### 最初の論点を忘れない
- 複数ターンの議論で、最初に置いたフレームから外れない
- ズレたら素直に「ズレてました」と訂正する

### プロジェクトドキュメントから読む
- 設計相談を受けたら、まずそのプロジェクトのドキュメント（`docs/`, `packs/*/docs/` 等）を読んでから答える
- 一般論や教科書的な答えから入らない

### 探索系の質問は短く返す
- 「どうしたらいい？」「どう思う？」系の質問は 2-3 文で推奨案＋トレードオフを返す
- 同意を待ってから実装する。勝手に手を動かさない

## 開発

### YAGNI と KISS
- 今必要なものだけ実装する。将来の要件のための抽象化は禁止
- 3つ似た行があっても早すぎる抽象化より許容する
- バグ修正に周辺クリーンアップを混ぜない

### コメント
- デフォルトはコメントを書かない
- WHY が非自明な時のみ書く（隠れた制約・微妙な不変条件・特定バグの回避策）
- WHAT は識別子の命名で表現する。WHAT を説明するコメントは書かない
- 差分依存コメント禁止（「〜しない」「〜を削除した」等、変更前を知らないと意味不明なもの）

### コミット
- ユーザーが明示的に依頼した時のみ作成
- `git add -A` / `git add .` を使わず、ファイル名指定で stage する
- destructive な git 操作（`reset --hard`、`push --force` 等）は事前確認

## ツール

### AI-TDD ワークフロー
TDD で実装したい時は `/tdd-orchestrator <plan.md>` を使う。
3つの隔離 agent (test-writer / implementer / refactorer) で Red→Green→Refactor を直列実行する。
詳細: `~/dev/dotfile/claude/docs/TDD-with-ai.md`
