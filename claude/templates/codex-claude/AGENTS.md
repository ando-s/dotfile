# エージェント向けルール

<project> で作業するエージェント（Codex、Claude Code など）共通のルール。`CLAUDE.md` はこのファイルを読み込むだけにしている。

## 役割分担

| エージェント | 担当 | 触らないもの |
|---|---|---|
| Codex | アプリの実装・テスト・デプロイ。実装の文脈（設計の細部、試したこと、残る課題）を持ち、`docs/progress.md` と `docs/worklog.md` に残す | ハーネス（下の行）の構成を変えるときは、Claude Code に任せるか本人に確認する |
| Claude Code | ハーネスの整備と更新：`AGENTS.md`、`.claude/`（スキル・フック）、`scripts/check_docs.py`、文書の置き場所と構成、決定記録と `docs/product.md` の更新手順 | `app/`、`tests/`、デプロイ。実装が必要な変更は `docs/progress.md` に書き、[delegate-to-codex](.claude/skills/delegate-to-codex/SKILL.md) の手順で Codex に渡す |

## エージェント間の連携

Codex と Claude Code は Herdr の別々のペインで動く。片方が作業を終えたことにもう片方が気づかず、ずっと待ち続ける状態を作らないため、次を守る。

| 場面 | すること |
|---|---|
| Claude Code が Codex に依頼したとき | 依頼の直後に、裏で `scripts/watch_agent.sh <project>-codex` を走らせる。状態に加えて画面の変化を見るので、Codex が終了・停止（承認待ちなど）・接続切れ・画面が動かない・時間切れのどれになっても、Claude Code が起こされて状態を確かめ、本人に報告する。手順は [delegate-to-codex](.claude/skills/delegate-to-codex/SKILL.md) |
| Codex が依頼を終えたとき・判断が必要で止まるとき | `herdr agent prompt <project>-claude "Codex: <終わったこと／止まった理由>。詳細は docs/progress.md"` で知らせてから終える。送れない場合（名前が見つからないなど）は `docs/progress.md` にだけ書いて終える |
| 知らせを受けたとき | 返事のためだけに相手へ prompt を送らない。新しい依頼があるときだけ送る（送り合いが続くのを防ぐ） |
| 承認・質問の画面で止まっているとき | 相手のエージェントが代わりに答えない。本人に伝える |

名前（`<project>-codex`、`<project>-claude`）はエージェントを起動し直すと消える。見つからないときは `herdr agent list` でこのリポジトリを開いているエージェントを探し、`herdr agent rename <ペインID> <名前>` で付け直す。

## 作業の始めと終わり

- 始める前に `docs/progress.md` を読み、必要なら `docs/product.md` を読む。
- 終えたら `docs/progress.md` の状態を更新する。実装・検証・公開をしたら `docs/worklog.md` に日付つきで追記する（過去の記録は書き換えない）。
- 文書を変えたら `python3 scripts/check_docs.py` を実行し、リンク切れと README からたどれない文書がないことを確かめる。

## 設計の方針（変更しやすさ）

方針は今後も変わる前提で作る。変わりそうな部分は、1か所を直せば済むように分けておく。

| 変わりそうなもの | 作り方 |
|---|---|
| 保存先 | 保存は1つの境界（読み書きの関数群）を通す。画面や処理から保存先を直接呼ばない |
| しきい値・初期設定・判定基準 | コードに埋め込まず、データファイルか設定値に置く。判定は差し替えられる関数1つにまとめる |
| AIのモデル | モデル名は環境変数で切り替えられるようにする |
| AIへの指示 | 決定に関わる指示は1か所にまとめ、決定記録を変えたときに探しやすくする |

ただし、今必要のない抽象化はしない。上の表にない部分は、素直に書く。

### 区切りの整理

機能の区切り（デプロイの直前）に、その区切りで触ったファイルだけを対象に整理を1回挟む。次のどれかに当てはまるときだけ行う。

- ファイルが約500行を超えた
- 同じ処理が3か所以上に出てきた
- 決定に関わるAIへの指示が1か所にまとまっていない

整理では振る舞いを変えない。自動テストが整理の前後で同じく通ることを確かめ、`docs/worklog.md` に何を分けたかを書く。機能の追加と同じ区切りの中で混ぜない。

## 公開と費用

- テストが通ったら、確認なしで <デプロイ先> にデプロイしてよい。デプロイしたら `docs/worklog.md` に revision とヘルスチェックの結果を書く。
- 必要な Google Cloud のサービスは確認なしで有効にしてよい。実行用サービスアカウントには必要な権限だけを足す。
- プロジェクト `<gcp-project>` には予算アラートを設定しておく（目安：月 ¥<金額>）。
- コミットと push は本人の依頼があったときだけ行い、`git add -A` や `git add .` を使わずファイルを指定して載せる。

## 本人の確認が必要なもの

<マイク・音・見た目など、AIだけでは確かめられないもの> は、自動テストで代わりに確かめられる範囲を確かめ、残りは本人が行うための手順書と質問票を用意して `docs/progress.md` に「本人の確認待ち」と書く。承認や質問の画面で止まったときも、本人に伝える。

## 文書の置き場所

| 書くこと | 置き場所 |
|---|---|
| 現在の仕様・決まっていること | `docs/product.md` だけ。他の文書には写さずリンクで参照する |
| 決定の理由と変更の履歴 | `docs/decisions/`（1決定1ファイル） |
| 作業の状態 | `docs/progress.md` |
| 実装・検証・公開の履歴 | `docs/worklog.md` |
| 確認方法と頻度 | `docs/verification.md` |
| 調査・比較 | `docs/research/`（調査日を書く。決定ではない） |
| 未決定の構想 | `docs/proposals/` |

新しい文書を作ったら README の「文書」の表からたどれるようにする。

## 方針を変えるとき

決まっていることを新しく決めたり変えたりするときは、[.claude/skills/decision-change/SKILL.md](.claude/skills/decision-change/SKILL.md) の手順に従う。要点：決定記録を足す → `docs/product.md` を直す → 影響する文書・コード・画面の文言を検索して揃える → `docs/progress.md` を更新する。

## 開発コマンド

```sh
<テストコマンド>
python3 scripts/check_docs.py
<デプロイコマンド>
```

確認方法と頻度は `docs/verification.md`。computer 機能での確認は原則として使わない。

## 書き方

- 日本語で書く。見出しは内容が分かる名前にし、比較には表を使う。ファイル名は小文字とハイフン。
- 決定・提案・未検証を区別して書く。会話の経緯（「〜と言われた」）は書かない。
- 「複雑」「リスク」のような抽象的な言葉で済ませず、何がどう問題かを書く。業界内でしか通じない言葉は言い換える。

## 扱いに注意するもの

- 認証情報や個人の記録・録音をコミットしない。例には架空のものを使う。
- 保存・同意・削除の方針を変えるときは、必ず決定記録を足す。
