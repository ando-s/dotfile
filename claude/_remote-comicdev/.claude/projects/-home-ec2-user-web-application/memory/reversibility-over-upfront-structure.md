設計改善を提案したとき、ユーザーは「後で変更しやすいか」で採否を判断する。後から変えやすい部分（テーブルの移動、列の追加）は多少の依存を許容し、後から変えにくい部分（参照の向き、外部キーを捨てる、型名をデータに焼く）だけを議論の対象にする。

**Why:** 要件になっていない将来（決済システムの追加など）に対して構造を先回りすると、要件が来たときに作り直しになって二度払いになる。可逆なものは後回しでコストが増えない。

**How to apply:** 改善案を出すときは利得だけでなく「後から入れる場合のコスト」と「今入れて失うもの」を並べる。要件が未確定なら実装せず、plan に「増やすときに触る場所」と代替案・判断の時期を記録して可逆性を担保する。読み口を1メソッドに閉じるなど、DB を変えずに変更点を1箇所にする手は今やる価値がある。NATSCREAF-76（MR!16889）でこの形に落ち着いた。[[tickets-adrs-not-binding-during-rework]]
