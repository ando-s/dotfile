[[extract-review-comment-learnings-skill]] の手順3（既存ドキュメント確認）で重複を見落とした。2026-07-01実行時、`code-review-patterns.md`に「イベントの多重度に応じてunique制約・has_manyを機械的に決める」という新セクションを追加したが、既存の別セクション（「イベントテーブルへの範囲条件は単一EXISTSで判定する」）の**検出シグナル箇条書きの中**に同じ核心（has_oneはAPI規約に過ぎず一意制約が必要）が既に書かれていた。見出し一覧だけを見て「新規テーマ」と判断し、既存セクション内部の箇条書きまで読まなかったのが原因。ユーザー指摘で削除。

同時に、「created_atの等価比較はDB精度(reload)に揃える」という学びも反映したが、ユーザーから「いらない気がする」と指摘され削除した。汎用的なレビュー観点というより、そのMR固有のテスト実装で一度だけ踏んだ実装トリビア（ns/μs精度差）で、他のレビューで検知シグナルとして機能する再利用性が薄かった。

**Why**: 既存ドキュメントとの重複マージ（review-update skillの原則）を怠ると、同じ趣旨が別々の場所に散って矛盾・冗長化する（[[pending-review-learnings-dedup]]で過去にも発生した同種の問題）。また、narrow/一度きりの実装詳細をパターン化すると、本当に汎用的な学びと同列に扱われ、ドキュメントの信号対雑音比が下がる。

**How to apply**:
- 既存ドキュメントを読むとき、見出し名の一致だけでなく、各セクション内の「検出シグナル」「判断軸」等の箇条書き項目まで全文読んで、核心の主張が重複していないか確認する
- 新しい学びの検証観点（手順4の「別の担当者のレビューで検知できるか」）に加え、「これは複数の場面で再現しうる構造的な問題か、それとも今回のMRでしか起きない実装詳細か」を自問する。後者なら学びとしない
