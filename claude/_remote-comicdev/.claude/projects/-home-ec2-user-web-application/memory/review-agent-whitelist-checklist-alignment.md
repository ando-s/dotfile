条件付き/自己判定型のレビューサブエージェント（payment-critical-reviewer 系）を作るとき、**対象範囲（発火対象＝どのファイルを見るか）とチェック観点（何を見るか）を整合させる**。チェック観点が対象にしたいファイル種別が対象範囲に無いと、チェックが適用される前にファイルが「対象外」判定されて見逃す。

なお呼称は「対象範囲」を使う（カタカナの「ホワイトリスト」は使わない。ユーザー方針）。

**具体例（NUTSKAIZEN-662, MR!16757）:** nuts-spica-boundary-reviewer に「語彙変換点（ベンダー語を公開I/Fに漏らさない）」のチェック観点があるのに、対象範囲に Nuts 公開I/F（APIコントローラ等）が無かった。結果、controller の `sps_cust_no`（SBPS電文項目名）露出を、チェック適用前に対象外にして見逃した。対象範囲に「Nuts利用者向け公開インターフェース」を追加して整合させ、再検証で検出を確認。

**2巡目で見つかった同型漏れ（同MR）:** クラス名の列挙（`Reader / Writer / Restorer / *Factory`）だけで発火対象を書くと、列挙に無い名前のクラス（Spica の列を Nuts 概念へ翻訳する変換クラス等、まさに語彙変換点）が対象外判定される芽になる。→ **ディレクトリ一致を主シグナル・クラス名の列挙は補助**にする。また観点が名指しする生フィールド（`continued_at` 等）の所有モデル（`::UserAnimeSubscription` 等）は定数例に必ず載せる。ユビキタス言語系は DB カラム名・マイグレーションも対象範囲に明記（永続化語が乗る）。

**修正の副作用は再走で炙る:** 対象範囲を広げると過剰検出・判定割れが新たに生まれる（「必ず含める」を違反判定と混同、基底コントローラの過剰包含）。修正後の定義を実ファイルに再走させ、新規対象が明示発火するか＋正常コードを偽陽性にしないかを確認する。

**How to apply:**

- エージェント新設・改訂時、各チェック観点について「その観点が見たいファイルは対象範囲のどの項目で入ってくるか」を1対1で確認する。
- 発火対象はパス（ディレクトリ）で表現し、クラス名・型名の列挙に頼らない（頼る場合は「補助」と明記）。勝手に型カテゴリ名を作らない（実在の役割名だけ使う）。
- **実際の違反を仕込んだ差分でエージェントを走らせて検証する**（正解キーは別管理でエージェントに渡さない）。`subagent_type` に登録済みなら直接、未登録でも定義を読ませて general-purpose に実行させればその場でテストできる。
- 見逃し・過剰検出・マーカーのランクを採点する。見逃しはたいてい対象範囲の漏れかチェック観点の粒度不足。修正後は再走して副作用（過剰検出）が無いか確認する。
- 対象範囲（対象パス）の追加/拡張で表現し、「〜しない/担当外」の除外ルールは書かない（ユーザー方針）。
- SKILL 側（呼び出し元）に対象範囲を重複列挙しない。対象範囲・チェック観点・出力形式はエージェント定義側が持ち、SKILL からはリンクと「自己判定させる」旨だけ書く（payment-critical-reviewer と同形）。
