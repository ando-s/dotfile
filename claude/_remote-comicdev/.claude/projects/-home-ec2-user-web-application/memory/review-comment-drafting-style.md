MR !16401 の方針コメント作成で s-ando から繰り返し受けた文面修正。

- **方針だけ書く。実装詳細（イベント名・メソッド名・トランザクション等）はコメントに入れない** — plan を書くのは相手。詳細はレイヤーが違う。入れるなら本文の下に「（提案メモ: 本筋とは別レイヤーの参考案です）」として区切る
- **指示形でなく依頼形**: 「〜してください」連発・「実装不要です」「確定で OK です」→「〜してもらえますか」「〜で大丈夫です」。相手の案を生かす前提（「考え方は活かしつつ」）を冒頭に置く
- **上から判定する響きの語を使わない**: 「〜してもらえれば十分です」の「十分です」が NG 例
- **対象外フローの否定説明を入れない**: 「全送信分は不要です（初回送信や同一 order_id 再送は…）」のような、変更対象でない処理をわざわざ否定する文は認知負荷。スコープは肯定文（「〜だけ入れる」）で伝わる
- **説明的な長い句より、名前の付いた概念1語**: 「新しい order_id を採番したときに送る前にそのorder_idを記録しておき…」→「order_id 採番イベントを追加する」
- **長い指摘は「概要 → 詳細 → 影響 → 依頼」の見出し構成にする**（MR !16384, 2026-06-12）。冒頭の太字見出し「概要」で結論を先に出し、トレースや列挙は後段の見出し配下へ
- **[ask] は自分で調べてから聞く**（MR !16384, 2026-06-12）。仕様書・コードで裏取りした内容を「調べた内容」として添え、残った不明点だけを質問にする。丸投げの確認依頼は不親切
- **件数を絞る。[nits] は基本出さない**（MR !16667, 2026-07-02「細かいコメント多すぎ」）。annotation不一致・コメント文言・schema.rbの並び順・周辺ドキュメントの旧称残存のような細かい指摘は下書きにしない。挙動・設計・運用リスクに直結する [must]/[should]/[ask] に絞る

- **文面は過去の s-ando のコメントに寄せる**（MR !17254, 2026-08-27「AIっぽさは消して」「もっと過去の s-ando のコメントを参考にして」）。実物は GitLab API で拾える（マージ済みMRの notes を author=s-ando で絞る）。特徴は次の通り
  - 1コメント2〜4段落。1段落1〜2文
  - 話し言葉。「〜してもらいたいです」「〜で大丈夫です」「〜と思います」「〜してもらえると嬉しいです！」
  - 根拠は1文で言い切る。ファイルパスと行番号の箇条書きを並べない
  - 提案する文言やコードは末尾にコードブロックで置く
- **英語の略語・カタカナ語を持ち込まない**: no-op、バックフィル、セーブポイント。挙動をそのまま日本語で書く（[[plain-language-no-jargon]]）

**Why**: コメントの読み手（業務委託メンバー含む）が一読で方針を掴めること、相手の設計を尊重した依頼に見えることが目的。社内ツール（Metabase 等）は説明を添え「こちら側で対応するので不要」を明示する（[[481-plan-review-direction]] 参照）。

**How to apply**: post_review_comment で下書きを作るとき、本文は方針の箇条のみ・依頼形・冒頭に相手の案の踏襲を明記。詳細案は末尾の提案メモへ。投稿前に「十分」「不要です（…のため）」のような判定・否定説明の語を点検する。
