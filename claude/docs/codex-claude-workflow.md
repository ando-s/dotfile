# Codex と Claude Code を組み合わせた開発の進め方

Codex と Claude Code を Herdr（コーディングエージェント向けのターミナル分割ツール）の別々のペインで同時に動かし、役割を分けて1つのリポジトリを開発するやり方。Cipher mate（`~/dev/rap-tailor`）で運用した形を、他のプロジェクトでも使えるようにまとめた。

雛形は [`claude/templates/codex-claude/`](../templates/codex-claude/) にある。導入手順は末尾の「新しいプロジェクトへの導入」。

## 全体像

| 置き場所 | 中身 | 誰が読むか |
|---|---|---|
| `AGENTS.md` | 両エージェント共通のルール（役割分担、連携、文書の置き場所、公開と費用） | Codex と Claude Code |
| `CLAUDE.md` | `@AGENTS.md` の1行だけ。ルールを2か所に書かない | Claude Code |
| `.claude/skills/` | 繰り返す手順（Codex への依頼、方針の変更、プロジェクト固有の評価） | Claude Code |
| `.claude/settings.json` | Stop フックで文書チェックを毎回走らせる | Claude Code |
| `scripts/check_docs.py` | リンク切れと README からたどれない文書を検出する | 両方・フック |
| `scripts/watch_agent.sh` | 依頼した Codex を見張り、終わった・止まった・詰まったで終了する | Claude Code |
| `docs/` | 仕様・決定・進捗・作業記録を分けて置く | 両方・本人 |

## 役割分担

| エージェント | 担当 | 触らないもの |
|---|---|---|
| Codex | アプリの実装・テスト・デプロイ。試したことと残る課題を `docs/progress.md`・`docs/worklog.md` に残す | ハーネス（下の行）の構成 |
| Claude Code | ハーネスの整備：`AGENTS.md`、`.claude/`、`scripts/check_docs.py`、文書の構成、決定記録と仕様書の更新、外部の基準（ハッカソンなど）での評価 | `app/`・`tests/`・デプロイ |
| 本人 | 方針の決定、承認画面への回答、マイク・音・見た目などの実機確認、利用者テスト | — |

分ける理由：

- 1つのエージェントに実装とルール整備を両方させると、実装の都合でルールが書き換わり、文書とコードが食い違っていく。ルール側を別のエージェントが持つと、変更が決定記録 → 仕様書 → 実装の順に流れる。
- Claude Code は実装を頼まれても自分で書かず、`docs/progress.md` に作業を書いてから Codex に依頼する。依頼の中身が文書に残るので、Codex を起動し直しても文脈が消えない。

## エージェント間の連携（取りこぼし防止）

一番効いた工夫。依頼したほうが相手の完了に気づかず、どちらも待ち続ける状態を作らない。

| 場面 | すること |
|---|---|
| Claude Code が Codex に依頼したとき | 依頼の直後に、Bash のバックグラウンド実行で `scripts/watch_agent.sh <proj>-codex 15 180` を走らせる。Codex が終了・停止・接続切れ・画面が動かない・時間切れのどれになっても Claude Code が起こされる |
| Codex が終えたとき・判断が必要で止まるとき | `herdr agent prompt <proj>-claude "Codex: <終わったこと／止まった理由>。詳細は docs/progress.md"` で知らせてから終える |
| 知らせを受けたとき | 返事のためだけに prompt を送らない（送り合いが止まらなくなる）。新しい依頼があるときだけ送る |
| 承認・質問の画面で止まっているとき | 相手のエージェントが代わりに答えない。本人に伝える |

補足：

- `herdr agent wait` だけでは足りない。Codex が接続切れで止まっても状態は working のままで、タイムアウトも効かないことがあった。`watch_agent.sh` は1分ごとに状態と画面を見て、「Reconnecting」などの表示や、15分画面が変わらないことでも終わる。接続切れのときは `herdr agent send-keys <proj>-codex esc` で止め、progress.md の再開位置を書いて依頼し直す。

- 依頼文は短くし、中身は `docs/progress.md` の行や決定記録を指す。依頼文に必ず「`AGENTS.md` と `docs/progress.md` を読んでから作業して」「終わったら `herdr agent prompt <proj>-claude` で知らせて」を入れる。
- 相手が working のときは送らず終わりを待つ。blocked のときは送らず本人に伝える。
- エージェント名は起動し直すと消える。`herdr agent list` で cwd がそのプロジェクトのペインを探し、`herdr agent rename <ペインID> <名前>` で付け直す。

手順は雛形の [delegate-to-codex](../templates/codex-claude/.claude/skills/delegate-to-codex/SKILL.md)。

## 文書の置き場所

仕様を1か所にだけ書き、他は理由・状態・履歴に分ける。同じことを複数の文書に写すと、片方だけ直されて食い違う。

| 書くこと | 置き場所 | 書き換えてよいか |
|---|---|---|
| 現在の仕様・決まっていること | `docs/product.md` だけ。他の文書からはリンクで参照 | 最新に書き換える |
| 決定の理由と変更の履歴 | `docs/decisions/`（1決定1ファイル、番号つき） | 書き換えない。変えるときは新しい番号を足し、古いほうを「置き換え済み」にする |
| 作業の状態と次にやること | `docs/progress.md`（表：順・作業・担当・状態・メモ） | 最新に書き換える |
| 実装・検証・公開の履歴 | `docs/worklog.md`（日付つきで追記） | 書き換えない |
| 確認方法と頻度 | `docs/verification.md` | 最新に書き換える |
| 調査・比較 | `docs/research/`（調査日を書く。決定ではない） | 調査時点の記録として残す |
| 未決定の構想 | `docs/proposals/` | 決まったら決定記録と product.md に移す |

新しい文書は README の「文書」の表からたどれるようにする。`scripts/check_docs.py` が README からのリンクをたどり、たどれない文書とリンク切れを報告する。Stop フック（`--hook` 付き）で Claude Code の応答が終わるたびに走るので、文書を足してリンクを忘れると、その場で直させられる。2回目の Stop では止めない作りにしてあり、直せない問題で終われなくなることはない。

## 方針を変えるときの順序

[decision-change](../templates/codex-claude/.claude/skills/decision-change/SKILL.md) の手順。

1. 何をどう変えるかを一文にする。曖昧なら本人に聞く。
2. 決定記録を足す（既存の決定を変えるなら古いほうを「置き換え済み」に）。
3. `docs/product.md` を直し、決定記録へのリンクを付ける。
4. 決定に関わる言葉で `rg` し、画面の文言・AIへの指示・構成図・提案書など文書の外にある同じ決定も揃える。`worklog`・`archive`・`decisions`・`research` は履歴なので直さない。
5. 残った作業（実装・デプロイ）を `docs/progress.md` に書き、Codex に依頼する。
6. `python3 scripts/check_docs.py` を走らせる。

キーワードの説明文に「〜にしたい」「やめる」「名前を変える」などを入れておくと、スキル名を言わなくても方針変更の依頼で手順が呼ばれる。

## 変わりそうな部分の作り方

方針は変わる前提で、変わりそうな部分だけを1か所に寄せる。それ以外は素直に書く（今必要のない抽象化はしない）。

| 変わりそうなもの | 作り方 |
|---|---|
| 保存先（ブラウザ・サーバー） | 読み書きの関数群1つを通す。画面や生成の処理から保存先を直接呼ばない |
| しきい値・初期設定・判定基準 | データファイルか設定値に置く。判定は差し替えられる関数1つにまとめる |
| AIのモデル名 | 環境変数で切り替える（例：`LYRIC_MODEL`） |
| AIへの指示のうち決定に関わるもの（安全・好みの扱い） | 1か所にまとめ、決定記録を変えたときに検索で見つかるようにする |

## 区切りの整理

整理（リファクタリング）は機能追加と混ぜず、デプロイ直前の区切りに1回だけ、その区切りで触ったファイルに対して行う。対象は「約500行を超えた」「同じ処理が3か所以上」「決定に関わるAIへの指示が散らばった」のどれかに当てはまるときだけ。振る舞いは変えず、整理の前後で自動テストが同じく通ることを確かめる。

## 確認の分け方

| 確認 | いつ・どうやって |
|---|---|
| 自動テスト | 変更のたび。主な流れと細かい状態はここで確かめる。同じ画面確認が2回必要になったら Playwright のスクリプトにする |
| 実AIへのリクエスト | 生成・音声・プロンプト・認証を変えたときだけ。区切りでまとめて行う（費用がかかるため） |
| 公開版 | デプロイ後に1回。ヘルスチェックと主要 API を HTTP で叩き、revision と結果を worklog に書く |
| マイク・音・見た目 | AIにはできないので、本人向けの手順書と質問票を用意し、progress に「本人の確認待ち」と書いてまとめて行う |
| computer 機能・手動ブラウザ操作 | 原則使わない。他の方法で確かめられず先に進めないときだけ使い、理由を worklog に書く |

マイクは仮想マイク（Chrome の `--use-fake-device-for-media-stream`）で自動テストに載せられる。

## 任せてよいことを先に決めておく

確認待ちで Codex が止まる回数を減らすため、`AGENTS.md` に「確認なしでやってよいこと」を明記する。

- テストが通ったら Cloud Run にデプロイしてよい（worklog に revision とヘルスチェックを書く）。
- 必要な Google Cloud のサービスは有効にしてよい。実行用サービスアカウントには必要な権限だけを足す。
- 予算アラートを設定しておく（金額をプロジェクトごとに書く）。
- `docs/progress.md` の Codex 担当の行は、前の行が終わったら確認なしで次へ進んでよい。デプロイは作業ごとではなく区切りでまとめる。

逆に、保存・同意・削除の方針を変えるときは必ず決定記録を足す、認証情報や本人の録音はコミットしない、を書いておく。

## 新しいプロジェクトへの導入

```sh
cd <新しいプロジェクト>
cp -Rn ~/dev/dotfile/claude/templates/codex-claude/. .
```

`-n` で既にあるファイル（README など）は上書きしない。その場合は雛形の「文書」の表を手で足す。その後：

1. `AGENTS.md` の `<project>`・`<gcp-project>`・予算・開発コマンドを書き換える。使わない節（Google Cloud など）は消す。
2. `.claude/skills/*/SKILL.md` の `<project>` を置き換える（`rg -l '<project>' . | xargs sed -i '' 's/<project>/myproj/g'`）。
3. `README.md`・`docs/product.md`・`docs/verification.md` の中身をプロジェクトに合わせて書く（雛形は見出しと置き場所の説明だけ）。
4. Herdr で Codex と Claude Code をそれぞれ起動し、`herdr agent rename <ペインID> <project>-codex` と `<project>-claude` で名前を付ける。
5. `python3 scripts/check_docs.py` が「問題なし」になることを確かめる。

外部の基準で評価するスキル（ハッカソンの審査基準など）はプロジェクトごとに作る。rap-tailor の `.claude/skills/hackathon-fit/` が例：基準を読む → 実物で確かめた現状だけを根拠にする → 提出物の点検 → 基準ごとに5段階（中間は低いほうに寄せる）→ 点を上げる打ち手を3つまで → 評価履歴を追記。
