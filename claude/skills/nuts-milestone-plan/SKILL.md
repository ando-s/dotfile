# Nuts マイルストーン計画の見直しと反映

計画は 1 つの HTML（時点ごとの template を持つ）を正本にして、Artifact・Drive・Jira・ガントのシートへ同じ内容を写す。見直しのたびに「新しい時点」を 1 つ足し、古い時点は消さない。

## ⚠️ 守ること

- **頼まれていない前提を足さない。** 人の配置・契約の期限・引き継ぎ・誰がレビューするか・並走期間のような体制の話は、ユーザーが言ったことだけを書く。要るのに無いときは「未定」と書くか聞く。自分で置いた値（期間の見積もりなど）は返答で「私が置いた値」と明示する
- **見積もりの値は自分で疑う。** 「1か月」「3週」のような前の版の仮置きが根拠無く残っていないか、各帯を「何をする作業で、なぜその長さか」で見直す。根拠が無ければ短くするか「未定」にして理由を書く
- **詳細計画がある手段（深川さんの au など）は、NTMS の期日をその計画の終了日と同じにする。** 余裕は期日に入れず、項目のリスク欄に「＋何週」で書く（2026-10-27 に 1/29 と 1/25 の食い違いが出た）
- **安藤の設計レビューも帯にする。** 各手段の「_設計」「_要求と要件のすり合わせ」タスクを週ごとに並べ、3 の安藤の段に出す。同じ週に 3 本以上重なる案は出さない
- **隠れたバッファを入れない。** ターゲット（目標）／見積もり（予測）／コミットメント（約束＝日付＋スコープ＋スコープ外＋前提）を分け、リスクは「起きたら＋何週」と分けて書く
- **Jira・スプレッドシート・MR への書き込みは、図（HTML）をユーザーが見て了承してから。** 図の版を出すたびに変更点を 3〜5 行で示し、「図がこれでよければ反映に進む」と区切る
- 表示の設計が仕様。図と選択肢（案A／案B）を先に出し、ユーザーに選んでもらってから作り込む

## HTML の構造

```
<title>…</title> <style>…</style>
<div class="verbar"> [計画][根拠][運用方法] のタブ ／ 計画の時点 <select id="plan-select"> </div>
<div id="app"></div>            時点ごとの本文を描く先
<main id="howto" hidden>…</main> 運用方法（時点に依らない固定ページ。置き場所・作り・見直しの手順・時点の履歴）
<template data-plan="2026-10-22" data-label="2026-10-22 時点（…版）">
  <main>
   <div class="page" data-page="plan">  計画のページ
     ヘッダー（数字 4 つ: 約束・見積もり・最後の切替・安全側の約束、一行の結論）/
     1. 決済手段ごとの進み方（SVG。methods と bands から描く）/ 2. 何が何の前に要るか（流れ図、固定の HTML）/
     3. 人ごとの帯（people）/ 4. 届かなくなる条件（表: 何が起きたら・どうなる・項目）と決めてほしいこと（チェック）
   </div>
   <div class="page basis" data-page="basis" hidden>  根拠のページ
     約束（日付・スコープ・スコープ外・前提）/ 順序の制約（段階の 1 行と箇条書き。横断の制約はここにだけ書く）/
     項目一覧（<table id="items">。rows から描く。行を押すとパネル）/ 言葉
   </div>
  </main>
  <script type="application/json" class="plan-data">{date,start,end,goal,methods,bands,people,rows,epics}</script>
</template>
<script> 共通の描画（select の切り替え、帯、項目一覧、根拠のパネル、タブ） </script>
```

- `methods[]` は `{name, cls, impl:[開始,終了], switch, watch:[開始,終了]?, migrate, risk, note?, marks?, key}`。`key` は rows のキー（押すとパネル）。`bands[]` は全行にかかる縦の帯（停止・後片付け）
- `people[].bars` は `[名前, 開始, 終了, 薄く(0/1), 段, リスクで伸びる日数, 項目のキー]`。キーを付けた帯だけ押せる。日付は `"YYYY-MM-DD"` の文字列
- `rows` は `[キー, 項目, 担当クラス, 担当, 期間, 大きさ, 見積もりの根拠, リスク, 順序の理由, 注意の配列]`。項目ごとの根拠はここにだけ持つ（帯・1 の図・項目一覧のどれを押しても同じ行がパネルに出る）。「注意の配列」には手段固有の未確認・制約・祝日の含み・AF 実績での積み上げを入れる。未起票の項目のキーは `未起票（売上集計）` のように一意にする
- `epics` はキーごとの `[エピック, 期間]` の配列（決済手段ごとのエピック。パネルの末尾に出る）
- 横断の話（約束・順序の制約・届かなくなる条件・決めてほしいこと）は根拠のページと 4 に 1 回だけ書く。同じ理由を項目の行と両方に書かない。体制の表・段階の一覧・方針行の文・見直し前の日付は HTML に置かない（帯と時点の切り替えが担う。方針行の文はシート側）
- 担当が変わっても大きさ・根拠・リスクは変えない。変えるのは根拠が変わったときだけで、理由を書く
- 図は人の言葉より先に目に入るので、日付を変えたら methods・bands・people・rows・epics・流れ図の文・4 の表・根拠のページ・数字 4 つの全部を揃える（流れ図・4 の表・根拠のページ・数字は手書きの HTML）
- 新しい時点を足すときは、最新の template をコピーして `data-plan` と `data-label` を新しい日付にし、本文と JSON を書き換える。描画スクリプトは触らない
- URL の `#YYYY-MM-DD` でその時点を直接開ける

## 手順

### 1. 何が変わったかを聞き取る

ユーザーの言葉（体制の変更、レビューの指摘、決定）をそのまま受け取り、計画のどこに効くかを整理する。決済手段の順序には次の制約がある（計画文書より）。

- 継続課金決済の切替は月に 1 回しか機会が無い。1週の遅れが 1か月の遅れになる
- docomo（d払い）は切替前の課金の確定が Spica の月次バッチで切替後 3か月続く。同期書き込みの停止の 3か月以上前に切り替える（2027-06 に停止するなら 2027-03 が上限）
- 段階6（読み取りの付け替え。売上集計も含む）と Spica 側の撤去は停止の前。段階5（データ移行）は停止の前提にせず、段階8 の行の削除の前に終える
- d払いのデバッグは 2段階認証の端末が要る（フルリモートの業務委託には任せない）。PayPay と atone はブラウザとテストアカウント（SMS 認証コードは固定）で済む

### 2. 案を出して選んでもらう

配分が変わるときは案A／案B を短く並べ、推奨を付けて `AskUserQuestion` で選んでもらう。大きな組み替えを黙って進めない。

### 3. HTML を書き換える

正本の最新 template をコピーして新しい時点を足す（初回の見直しの日は既存 template を直接直してよい）。書き換えは python の文字列置換で、各置換に `assert s.count(a)==1` を付けて取りこぼしを防ぐ。JSON は `json.loads` → 書き換え → `json.dumps(ensure_ascii=False).replace('</','<\\/')`。

書き終えたら `references/reflect.md` の「HTML の検査と配布」で、描画の確認・Artifact 用ファイルの生成・Drive への流し直しを行う。

### 4. セルフレビュー

ユーザーに見せる前に、文書を通しで読み直す。

- 同じ日付が節をまたいで食い違っていないか（帯・項目の行・4 の表・根拠のページ・数字 4 つ・流れ図）
- 同じ理由・同じ未確認が複数の場所に書かれていないか（項目の話はその行の「注意」に、横断の話は根拠のページか 4 に 1 回だけ）
- 「最後の切替」「停止」「クリーンアップ」「保管」の順序が制約に合っているか（行の削除は保管の後）
- 案B の日付が「最後の切替が 1か月遅れた場合」の計算と合っているか
- 作成中のメモ（「この文書内で混在していた」「前の版は…」）が残っていないか
- 帯の開始日・終了日が土日・祝日・休業日に当たっていないか。`scripts/check_holidays.py` に正本と、統合シートの「休業日」シート（コネクタの `get_values` で `休業日!A2:B80` を読み、`{"values": [...]}` の形でファイルに書いたもの）を渡す。GW・年末年始を含む短い作業は 1 週伸ばすか避ける。マイルストーンのシートは週の列なので休日を見ない（日単位のシートだけが灰にする）
- ステークホルダー目線: 結論が先頭にあるか、判断をお願いしたいことが列挙されているか、内輪の言葉に説明があるか

### 5. 反映

ユーザーの了承後、`references/reflect.md` の順に書く。Jira の日付 → `_方針` → `_メモ` → `設定` → 計画文書の MR。終わったら「ガント：マイルストーンのシートは描き直してから使う」と伝える（`_メモ` と Jira を直接書いているため、シートは描き直すまで古い）。

### 6. 返答

変更点を箇条書きで 3〜5 行、⚠️ で残るリスクと未確認を分けて書く。自分で置いた値はそう書く。

## 書き方（HTML の文）

- 理由は制約だけ残し、経緯（「以前は」「当初は」「〜に変更した」）は書かない
- 日付は `M/D`、期間は `M/D〜M/D`。人は「深川さん」「鈴木さん」「正社員」「安藤」（自分は敬称なし）
- リスクは「＋何週: 何が起きたら」の形
- 未確認は「未確認」と書く。推測を事実のように書かない
