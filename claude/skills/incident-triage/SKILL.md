# incident-triage（インシデント調査）

Nuts（決済基盤）のアラート調査を、確認済みの事実と推測を分けて一本の報告にまとめる。

## 入力

Sentry の issue ID・URL、またはアラートの要約文。

## 手順

1. **Sentry から事象を取る。** Sentry MCP で issue の例外・件数・初回発生・最終発生・タグ（環境、ユーザー属性）を取り、時系列を押さえる。
2. **仕様の該当箇所を探す。** `packs/nuts/docs/` の `機能/{機能}/仕様.md`・`要件定義.md`、プロバイダ固有は `softbank/spec/` や `card/`。該当箇所をファイル名と見出しで示す。
3. **コードの経路を特定する。** Grep で例外の発生元から controller・モデル・プロバイダ層まで辿り、ファイル:行で示す。
4. **実データで影響範囲を数える。** `mcp__metabase__execute_sql` で件数・対象者・期間を出す。SQL と行数を報告に載せる。`-read__` はステージングなので使わない。
5. **本番リリースとの関係を確かめる。** 事象の開始時刻と production ブランチのデプロイ時刻を突き合わせる。デプロイは master パイプラインではなく production ブランチ（30分刻みの cron）。
6. **確認済みと推測を分けて書く。** 確認済みには根拠（SQL・行数・ファイル:行・Sentry の値）を添える。推測は「推測」と書き、確かめる方法を添える。換算係数・見積り数値を根拠なしに出さない。
7. **JIRA チケットの下書きを作る。** 見出しは 背景 / 完了の定義 / やらないこと / メモ の4つ。比較・計測結果は表にする。コードのファイルパスを含める。
8. **停止する。** 下書きを全文示して「この内容で作成していいですか」と聞く。承認後に `jira` CLI で作成する。

## 報告の形

- 事象（Sentry の値）
- 原因（ファイル:行、仕様の該当箇所）
- 影響範囲（SQL、件数、期間）
- 確認済み / 推測 の区分
- チケット下書き

## やらないこと

- 承認前のチケット作成・コメント投稿
- 根拠のない件数・時間の見積り
- 一般論での原因説明。コードと実データで裏取りできたことだけ書く
